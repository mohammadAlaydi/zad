# ADR-0008: KYC — provider adapter, status state machine, encrypted documents

- **Status:** Accepted
- **Date:** 2026-05-13
- **Deciders:** Engineering
- **Tags:** backend, mobile, security

## Context

The mobile app today has a full KYC capture flow ([app/(auth)/id-capture.tsx](<../../app/(auth)/id-capture.tsx>), [id-scan.tsx](<../../app/(auth)/id-scan.tsx>), [selfie.tsx](<../../app/(auth)/selfie.tsx>), [personal-info.tsx](<../../app/(auth)/personal-info.tsx>), [address.tsx](<../../app/(auth)/address.tsx>)) — but no upload, no verification, no status. We need a server side that handles uploads safely, calls a verification provider, and tracks status.

Engineering-only scope per the brief: build the right patterns; do not contract a vendor in P1.

## Decision

### Provider-adapter pattern

KYC providers (Sumsub, Onfido, Veriff, Jumio) all expose roughly the same shape: upload documents + selfie, return a verification result with checks. We abstract them behind a port:

```ts
// modules/kyc/domain/ports/KycProvider.ts
export interface KycProvider {
  createApplicant(input: ApplicantInput): Promise<Result<ProviderApplicantId, KycError>>;
  uploadDocument(
    applicantId: ProviderApplicantId,
    doc: KycDocument,
  ): Promise<Result<DocumentRef, KycError>>;
  submitForReview(applicantId: ProviderApplicantId): Promise<Result<void, KycError>>;
  verifyWebhook(headers: Record<string, string>, body: Buffer): Result<KycEvent, KycError>;
}
```

Phase 1 has **two** implementations:

- `InMemoryKycProvider` — deterministic, used in tests + dev (mirrors the demo's "auto-approve after 5s").
- `SumsubKycProvider` — real adapter, stubbed (no API key required at compile time; only when `NODE_ENV=production`).

The mobile flow is unchanged; the backend provider swap is a config change.

### Status state machine

```
not_started ──submit──▶ pending
pending     ──upload──▶ pending
pending     ──submit──▶ submitted
submitted   ──provider:review──▶ review
review      ──provider:approve──▶ approved
review      ──provider:reject──▶ rejected
rejected    ──resubmit──▶ pending
approved    ──admin:revoke──▶ rejected
```

- Transitions are enforced in the `KycApplication` aggregate (domain layer). Illegal transitions are domain errors.
- The state field is on `kyc.applications.status`. The aggregate carries the transition history in `kyc.applications.history` (JSONB) for audit. The cross-cutting `shared.audit_log` also gets a row per transition.

### Document handling — encrypted-at-rest, never on disk

- The mobile app **never** uploads documents to our origin server. It uploads directly to S3 (or equivalent) via a **presigned URL** issued by `POST /v1/kyc/documents/presign`. The API never sees the document bytes — this minimizes data exposure and keeps origin instances stateless.
- S3 bucket policy:
  - Server-side encryption with KMS (CMK per environment).
  - `PutObject` restricted to presigned URLs only.
  - Bucket has no public access; not in CloudFront; access via short-lived signed URLs (5 min TTL) when the verification provider fetches.
  - Lifecycle: documents older than 7 years auto-deleted (regulatory baseline).
- The presign endpoint:
  - Enforces user ownership (you can only presign documents for your own applicant).
  - Enforces MIME type (`image/jpeg`, `image/png`, `application/pdf`) and `Content-Length-Range` (e.g. 50 KB – 8 MB) in the policy.
  - Returns a unique S3 key per document attempt; never overwrites.
- After upload, the mobile calls `POST /v1/kyc/documents/{id}/notify` with the S3 key; we record `kyc.documents` row + push to the provider via `uploadDocument`.

### Webhooks

KYC providers report results asynchronously via webhooks. Our handler:

```
POST /v1/webhooks/kyc/sumsub
  → verifies signature (provider-specific HMAC, secret from env)
  → idempotency check (provider's event ID, dedup in Redis 7d)
  → converts to a domain event (KycApproved, KycRejected, KycReviewRequired)
  → applies via the aggregate, publishes the event on the bus
  → returns 200 quickly; downstream effects (user notification, role update) happen via subscribers
```

Webhook routes are **outside** the normal auth middleware — they authenticate via the provider's signature, not our JWT.

### Mobile flow

```
1. User picks doc type → app calls POST /v1/kyc/documents/presign with {type, mimeType}
2. App uploads to S3 directly with the presigned URL
3. App calls POST /v1/kyc/documents/{id}/notify
4. After all required docs uploaded, app calls POST /v1/kyc/applications/submit
5. App polls (or subscribes to push notifications, Phase 2) for status changes
6. On approve → JWT is refreshed; new access token carries kyc_status=approved
7. RootGuard ([ADR-0003]) lets the user past the auth group
```

The user-facing capture screens in `(auth)/id-capture.tsx`, `id-scan.tsx`, `selfie.tsx` migrate to use this flow — UI stays, the submit handlers change.

### Schemas (Phase 1)

```
kyc.applications
  id              uuid pk
  user_id         uuid                -- (no SQL FK across modules)
  provider        text                -- 'sumsub' | 'onfido' | 'inmem'
  provider_ref    text nullable       -- applicant id at the provider
  status          text                -- state machine value
  submitted_at    timestamptz nullable
  decided_at      timestamptz nullable
  rejection_reason text nullable
  history         jsonb default '[]'

kyc.documents
  id              uuid pk
  application_id  uuid references kyc.applications(id)
  type            text                -- 'passport' | 'national_id' | 'driving_licence' | 'selfie' | 'proof_of_address'
  s3_key          text
  mime_type       text
  size_bytes      int
  uploaded_at     timestamptz
  provider_ref    text nullable
  status          text                -- 'uploaded' | 'submitted' | 'accepted' | 'rejected'
```

### Privacy & retention

- We store metadata (status, timestamps, provider refs) indefinitely.
- We store document bytes in S3 with a 7-year lifecycle (regulatory minimum for the markets we plan to operate in — adjust per market).
- A user-deletion request triggers: bytes erased from S3 immediately; metadata rows tombstoned (zeroed PII columns) and retained for the regulatory window.
- KYC events that flow on the event bus carry **no PII** — only the application ID + the new status. Subscribers query for the data they need with their own permission scope.

## Consequences

**Positive**

- Provider-agnostic: swap Sumsub for Onfido in one config line.
- Origin servers never touch document bytes.
- Webhook handler is idempotent and signed.

**Negative**

- More moving parts than the naive "POST to /kyc with multipart" approach. Worth it for the security and ops gain.

**Neutral / accept**

- The mobile app needs S3 SDK or `fetch` to a presigned URL. We use `fetch`; no extra SDK.

## Alternatives considered

1. **Multipart upload through our API.** Origin sees document bytes; risk of leak; doubles bandwidth; complicates DDoS budget. Rejected.
2. **Custom in-house KYC engine (OCR + face match).** Multi-quarter compliance work. Not a sane build vs. buy here. Rejected.
3. **Per-environment hardcoded provider.** Couples us to one vendor. The adapter port is cheap insurance.

## Rollout

- PR-9: `kyc` module skeleton + applications/documents schemas + `KycProvider` port + `InMemoryKycProvider`.
- PR-10: Presign endpoint + S3 client wrapper + webhook receiver scaffolding.
- PR-11: Mobile KYC feature migration (existing screens → new endpoints).

## Revisit when

- We onboard a market that requires a specific local provider (e.g. UAE-issued IDs validated by a domestic KYC service).
- We need biometric re-verification for high-value transactions (step-up KYC). The state machine extends with a `re_verification_required` branch.
- We add corporate KYB (Know Your Business) — separate aggregate, separate state machine, separate provider list. Not a retrofit of this one.
